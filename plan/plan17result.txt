Installed Piper (piper-tts 1.8.0) CLI definition,

  - argparse parser defines: -m/--model (required), -c/--config, -i/--input-file,
    -f/--output-file/--output_file, -d/--output-dir, --output-dir-naming,
    --output-raw, -s/--speaker, --length-scale, --noise-scale, --noise-w-scale,
    --cuda, --sentence-silence, --volume, --no-normalize, --data-dir, --debug.
  - There is NO `--espeak-voice` option. Grep for "espeak" in that file: no match.
  - Line 102:  args, unknown_args = parser.parse_known_args()
  - Lines 117-123:
        if unknown_args:
            texts = [" ".join(unknown_args)]
        else:
            texts = sys.stdin
  - Line 125-129: lines() yields each non-blank stripped line of `texts`.

Consequence, derived from the source above:
  `--espeak-voice` and its value are collected into `unknown_args`, so
  `texts` becomes the literal string " ".join(["--espeak-voice", "<voice>"]) and
  `sys.stdin` is NEVER read. The UTF-8 subtitle payload the application carefully
  builds (stdin_payload, lines 473-484) is delivered on stdin and then discarded by
  Piper. Piper synthesises the literal text "--espeak-voice <voice>" instead.
  Because piper still exits 0 and writes a non-empty WAV, the application's own
  checks (returncode == 0, file exists, size > 0, frames > 0) all report SUCCESS.
  Audio that is not the subtitle text would be produced and presented as correct,
  for Preview Voice AND for every item of Generate All Voices.

  Scope: `resolve_espeak_voice()` (line 290) returns espeak.voice from the model
  config for all 17 discovered voices (see 5. static inputs), so the flag is
  appended in 100% of real cases with the current code.

  Why the existing tests do not catch it: every test in tests/test_piper_service.py
  either uses a fake Python script as `piper_cmd` (write_wav_fake_exe) or mocks
  services.piper_service.subprocess.run. The real piper-tts CLI argument parser is
  never executed, and no test asserts the exact full argv sent to a real Piper.
  tests/test_piper_service.py:825-827 asserts only the first three argv entries.

  STATUS: STATIC FINDING, NOT EXECUTED, NOT FIXED. It must be confirmed on a
  working machine by running tests/manual_piper_runtime_check.py and listening to
  (or inspecting the SHA256/duration of) the produced WAV, and by running
  `uv run python -m piper --model <model> --espeak-voice vi --output_file x.wav`
  with no stdin versus with stdin. This is the most likely mechanical explanation
  for the "preview audio is wrong" symptom that PLAN 15 FIX 2 was chasing, and it
  would apply identically to the module route and to the in-project piper.exe, so
  it is a better candidate explanation than a PATH/module runtime mismatch.
